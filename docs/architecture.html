OnlyDiffs architecture

A desktop git diff viewer built on Tauri 2, with a Rust backend that shells out to git and a React renderer that never touches the filesystem. This is the map: what the pieces are, which one calls which, and where the decisions live.

Version 0.1.6 · 2,926 lines of Rust, 5,163 of TypeScript in the desktop app · 52 Rust tests, 21 renderer tests

1. The shape of the thing

OnlyDiffs shows you the working tree of one git repository and lets you talk to a Claude Code session about a specific line of it. That is the whole product. Everything below serves those two jobs.

The app runs as two processes that Tauri glues together. A Rust backend owns all state that outlives a render, spawns every git child process, and holds the only network clients. A React renderer draws, and asks the backend for data through a typed command bridge. The renderer has no filesystem access and no way to run a subprocess, which is the point: a compromised page cannot reach the repository except through the seventeen commands the backend chooses to expose.

Turbo passes exactly three environment variables through to tasks: ONLYDIFFS_REPO_PATH, ONLYDIFFS_STATE_DIR, and GROQ_API_KEY. That list is worth knowing, because those three are the only knobs the app reads from its environment.

A released bundle has no shell behind it. Finder, Spotlight, and the Dock hand a process launchd's environment — fifteen variables, no .zshrc — so a key exported for every terminal on the machine is simply absent, and both Groq features go quiet in exactly the build where nobody is watching a console. services/shell_env.rs closes that gap: the process environment wins where it has the variable, and otherwise a login shell is asked once per launch, on the first Groq call rather than at startup, so a dev build never pays for it.

The environment is the fallback, though, not the interface. services/settings.rs owns ~/.onlydiffs/config.json, written 0600 beside the recents file, and a key saved from the settings page beats GROQ_API_KEY — it is the only one of the two the user can see from inside the app, so a variable exported months ago and forgotten must not silently outrank it. Clearing the field hands the app back to the environment. The key itself never crosses to the renderer: the page is sent a masked hint and the name of the source that won, which is all it needs to say a key is set and all it should hold in a webview that also renders untrusted diff text.

Since v0.1.8 that environment is only half the story, because a repository need not be on this machine at all. src-tauri is a workspace of three crates: onlydiffs is the app, onlydiffs-core is everything that runs where the repository is, and onlydiffs-agent is that core running on a host and speaking a framed protocol on stdio. Core carries no tauri dependency and its manifest is what keeps it that way — the agent is cross-compiled for Linux, where there is no webview to link against.

services/repository.rs is the seam. It holds a root and the machine that root is on, and its methods are deliberately coarse: diff() is one question with one answer, not git() called once per changed file, because the local walk costs one invocation per file and running that over a network would be several hundred round trips for one screen. The remote variant holds a channel rather than a connection, which is what keeps SSH out of core entirely.

3. The command bridge

This is the most opinionated part of the codebase and the part most worth copying.

Tauri commands normally return Result<T, E>, and a returned Err gets stringified on its way across. That flattens a structured failure into prose and throws away the discriminant. OnlyDiffs refuses to lose that. Every command returns Result<IpcResult<T>, ()>, where the error case is a value inside a successful response: 

{ ok: true,  value: T }
{ ok: false, error: { _tag: "GitError", message: "..." } }

The renderer's call() in lib/ipc.ts unwraps that and throws an IpcError carrying both tag and operation. Callers that only want a string read it as an ordinary Error. Callers that need to branch match on the tag. A genuine Tauri rejection, meaning a missing command or a payload that failed to deserialize, folds into the same error type with the tag ChannelError.

AppError has nine variants and tag() maps each to a string. Those strings are load-bearing contract, not debug output.

4. Backend

AppState and startup

lib.rs builds one AppState and Tauri manages it for the process lifetime.

FieldPurpose
workspaceWhich repository is open, and the remembered list of them.
watcherThe active filesystem watch. Moves when the project changes.
httpOne pooled reqwest::Client shared by Groq and the Claude channel.
icon_resolutionA mutex that stops startup and a fresh open_project from running overlapping icon passes.
pending_updateThe update handle from the last check, held so installing applies the version the user was offered.

Startup runs in this order:

  1. Workspace::from_env() reads ONLYDIFFS_STATE_DIR and ONLYDIFFS_REPO_PATH, loads projects.json, and opens either the pinned repository or the most recently used one that still exists on disk.
  2. setup() starts watching that repository. This happens here rather than in AppState::new because there is no AppHandle to emit through yet.
  3. The window is built at 1100x760, minimum 720x480, and hidden.
  4. A task sleeps 3 seconds and shows the window regardless. That is a safety net for a renderer that throws before it can show itself.
  5. A second task sleeps 500ms, then starts icon resolution, so Groq calls never delay the first frame.
  6. The renderer shows the window itself, on the second animation frame after first render. That is the earliest moment the page is genuinely painted.

on_navigation runs is_internal() on every attempted navigation. tauri:, asset:, and loopback HTTP pass. Everything else is handed to the system browser and the navigation is refused, so no link can replace the app with a web page.

git.rs

Three functions: run_in(cwd, args), run(workspace, args) which resolves the current repository first, and show_file(workspace, revision, path) where an empty revision means the index.

Two details here are not stylistic. It uses output() rather than spawning and waiting, because output() drains stdout and stderr while it waits, and a patch larger than the OS pipe buffer would otherwise deadlock the child forever. And it treats non-empty stdout as success even on a non-zero exit, because git diff --no-index exits non-zero precisely when it did produce a patch. Decoding is deliberately lossy, so one stray byte renders a file rather than blanking the card.

diff.rs

The busiest module. Five public functions.

get_diff is the startup read. It runs three git commands concurrently through try_join!: rev-parse --abbrev-ref HEAD for the branch, log -1 for the head line, and status --porcelain -z -uall for the changes. The -uall matters, because without it an untracked directory collapses into a single record and you cannot diff a directory.

parse_porcelain splits that status output into Side records, one per changed half. A path that was edited, staged, then edited again produces two of them, because those are genuinely two different patches. Then the per-file patches run through stream::buffered at a concurrency of 8, and results sort by path with the staged half first.

get_file_contents is deliberately a separate command. If it were folded into get_diff, startup would read every changed file in full. Instead the cards ask for their own contents as they approach the viewport.

Path safety lives in is_safe_repo_path and validate_path. Paths arrive from the renderer, so .., a leading separator, and a Windows drive letter are all rejected before anything is handed to git show or joined onto the root.

commit_all runs git add -A and then git commit -m, rather than commit -a, because -a skips untracked files and that is not what a user means by "commit all". The message goes through -m as one argument, so nothing in it reaches a shell or is read as a flag.

commit_message_diff assembles the whole working tree into one annotated document for the model, with each patch under a ### staged:, ### unstaged:, or ### untracked: heading.

workspace.rs

Holds current: Mutex<Option<PathBuf>> and recents: Mutex<Vec<StoredProject>>, persisted to ~/.onlydiffs/projects.json at schema version 1. Opening a path walks up to find the repository root, so opening any file inside a checkout opens the checkout.

Two ordering decisions are easy to get wrong. The project list keeps first-opened order rather than most-recent order, so switching projects never makes the rail jump around under the cursor. Restoring at startup uses last_opened_at separately, and that timestamp is kept strictly increasing even when two opens land in the same millisecond. Entries whose folder has since vanished are skipped rather than deleted, so unplugging a drive does not erase history.

project_icon_jobs() and record_icon_scan() are the icon resolver's view of this store. Jobs sort the currently open project first.

watcher.rs

Before this existed the diff only refreshed when a route loader ran, which made a stale view the default: an agent could rewrite twenty files and the screen would not move until you navigated. Now the backend pushes.

ChangeFilter applies the repository's own ignore rules through the ignore crate, so node_modules and target never produce an event, and is_git_signal lets through the few .git entries that actually mean something while dropping the rest. What survives is debounced at 300ms and emitted once as repo:changed. A thirty-file rewrite is one refresh.

claude_channel.rs

Claude Code sessions advertise themselves by writing a JSON file into ~/.onlydiffs/claude-channels/. A registration carries a schema version, a port, a bearer token, a pid, and the working directory.

registrations() reads that directory and keeps a file only if the schema version matches, the port is non-zero, the token is non-empty, the cwd normalizes to the open repository, and the process is still alive. The liveness check is last on purpose, because it is the only one that costs a syscall. Survivors sort newest first. Half-written and stale files are skipped in silence rather than raised, since the next candidate may well work.

send() posts to 127.0.0.1 with the token, capped at 64KB and 10 seconds. The channel is one-way by design. It resolves with a message id, which is only useful for correlating logs, and whatever Claude does next happens in Claude Code.

The two Groq integrations

Both read GROQ_API_KEY from the process environment. The key never reaches the renderer bundle.

The icon resolver is the more interesting of the two. It ranks candidate image files by name (icon and logo score high, anything matching screenshot or banner is penalized 100), takes the top 32, renders each to a 256px PNG, drops byte-identical duplicates, and sends at most three to the vision model. Three is not a taste decision. Groq rejects a request carrying more than three images. SVGs rasterize through resvg with no resource directory, so a candidate cannot read sibling files or fetch a remote URL while being rendered.

The model may also decline every candidate, and that is a real answer rather than a failure. A repository whose only image is a screenshot keeps the cube. The result is keyed by a hash of the candidate shortlist, so an unchanged repository is never sent twice. A failed Groq call stops the whole pass rather than retrying per repository, because a rejected key or a retired model will fail identically for every project still queued.

5. Renderer

Entry and routing

main.tsx awaits currentProject() at module scope and picks the starting route from the answer: / when nothing is open, /diff otherwise. Deciding it here rather than redirecting out of / keeps the picker reachable, since the sidebar's link to / still lands there.

The router uses createMemoryHistory, not hash history. WebKit binds Backspace to its own page history even while a text input is focused, so hash routes meant that deleting text in the command palette could navigate out of the repository. A desktop window has no URL to restore anyway.

StrictMode is on, and the comment explaining why the first diff blanks in dev is worth reading before anyone "fixes" it: @pierre/diffs writes imperatively into a shadow root, and the simulated unmount tears that down.

file-diff-card.tsx

Three mechanisms worth knowing. An IntersectionObserver with a 600px margin sets shouldRender, so a repository with eighty changed files does not fetch eighty file bodies at once. A module-level WeakMap keyed on the FileChange deduplicates in-flight content requests, so two cards for the same object share one promise and the entry is collected with the object. And DiffBoundary is a class error boundary, because @pierre/diffs parses patches at render time and a malformed one should cost a card, not the window.

The single-file route skips the observer entirely. There is exactly one card and it is always in view, and waiting on an observer there can strand the card if the pane has not been laid out when the observer starts.

app-file-tree.tsx

lib/file-tree.ts splits the work in two on purpose. buildFileTree is O(paths) and runs once per repository load. flattenTree runs on every expand, collapse, and keystroke, so it stays cheap. Runs of single-child directories fold into one row, which is why you see .github/workflows rather than two levels.

Rows are 26px. Virtualization switches on above 150 rows rather than always, since a virtualizer costs more than it saves on a short list. The filter goes through useDeferredValue so typing never blocks on a re-flatten.

7. The Claude Code channel

scripts/claude-channel.ts is the other half of the bridge, registered as a user-scope MCP server by bun run channel:setup. One script does two jobs at once.

It connects to Claude Code over stdio as an MCP server, declaring an experimental claude/channel capability and instructions telling Claude that arriving messages come from the user working in this repository. Separately it starts a Bun HTTP server bound to 127.0.0.1 on port 0, so the OS picks a free port. A 32-byte random token guards it, compared with timingSafeEqual. Then it writes its registration file with mode bits restricted, and removes it on exit.

So the full path from a click to Claude runs: a diff line click sets the line reference, the toolbar composer sends the text, send_claude_message reaches claude_channel::send, which finds the live registration for the open repository and POSTs to its loopback port with the token, and the script forwards it into the MCP session. Nothing comes back.

9. Build and release

bun run dev at the root runs every workspace through Turbo; dev:desktop filters to the app. Inside apps/desktop, tauri dev starts Vite on a fixed port 1420 and fails loudly on a clash, because silently serving somewhere the window will not look is worse than stopping.

bun run build is typecheck, then tests, then the Vite build. bun run dist bundles: dmg and app on macOS, nsis on Windows, appimage and deb on Linux. The updater plugin is compiled in only for desktop release builds, since it reads a signing key at startup that a dev build has no use for.

Three webviews, and it is worth remembering which is which. Windows gets WebView2, which is evergreen Chromium. macOS gets WKWebView and Linux gets WebKitGTK, both WebKit. Two of the three targets are WebKit, so a WebKit-only rendering bug is the default case here, not an edge case.

10. Things I would flag to a new contributor

The contract files are duplicated by hand. contract.rs and contract.ts mirror each other with a comment in each asking you to update the other, and nothing enforces it. A field added on one side and forgotten on the other typechecks fine and fails at runtime. That is the highest-risk seam in the codebase.

Failure handling is not uniform, and mostly for good reasons. A failed update check stays silent because the user did not ask and offline is a laptop's normal state. A failed icon resolution logs and keeps the fallback. A failed commit-message generation goes straight to the palette. Those are three different policies, and each is defensible, but you have to read each one to know which you are in.

The renderer holds no cache of its own. Every refresh path funnels into router.invalidate() on the /_app loader, which is why refresh, the watcher, focus, project switching, and icon resolution all take the same code path. It is a simple design that has held up, though it does mean any refresh re-reads the entire diff.

11. Architecture review: deepening opportunities

Four places where the current shape costs something. Each is judged on depth, meaning how much behaviour a caller or a test gets per unit of interface it has to learn, and on where the seam sits. The repository has no CONTEXT.md and no ADRs, so the domain names below are the ones the code already uses: Workspace, Project, RepoDiff, Side, ProjectIcon.

Scope came from the churn. app-command-menu.tsx is the most-edited source file in the last sixty commits, the IPC seam has been rewritten twice (Electron to Tauri, then Effect out of the IPC layer), and the project and icon cluster is where the newest 829 lines landed.

A. Opening a project is written three times, and the three disagree

Strong
Files
project-sidebar.tsx:30, app-command-menu.tsx:128, routes/index.tsx:65
Problem
All three run the same sequence: mark busy, call openProject, navigate to /diff, refresh loaders, catch, clear busy. They do not agree on the last details. The rail and the palette pass replace: true and then call router.invalidate(); the landing page passes neither. Both behaviours are defensible, because entering /_app from / runs the layout loader anyway and there is no file route to replace. Nothing says so. A reader cannot tell the difference between a considered choice and an oversight, which is what makes it a locality problem rather than a bug.
OtherProjectsSection is the sharper symptom. It takes seven props, four of them lifecycle callbacks (onStart, onOpened, onError, onFinish), to wrap about thirty lines. Its interface is nearly as large as its implementation, which is the definition of a shallow module. Deleting it would move those lines back to its parent rather than concentrate anything.
Solution
One project-opening module, useOpenProject(), returning { open, opening, failure }. The navigation rule moves inside it, stated once: replace the route when already inside /_app, invalidate when the loader will not re-run on its own. The three call sites keep their own presentation and lose their copy of the sequence. OtherProjectsSection collapses into the palette that holds it.
Benefits
Leverage across three call sites for one interface of three names. Locality for the ordering rule, which is currently implicit in three files. For tests this is the clearest win: today the sequence is only reachable by rendering three components, and it is untested in all three. Behind one module it becomes one thing to test.

B. The icon resolver's decisions cannot be reached through its interface

Strong
Files
services/project_icon.rs:435 (resolve_job), :472 (resolve_missing)
Problem
resolve_missing(&AppHandle, &Workspace, &Client) needs a live Tauri handle and a working Groq key to run at all, so no test calls it. The twelve tests in this module reach past the interface to internals instead: discover, selection, scan_hash, name_score, request_content. Neither orchestration function is imported by any test.
That leaves the decisions about whether a project gets an icon at all completely uncovered: the unchanged-hash short circuit, recording an empty shortlist, recording a model refusal, and the split between a per-project failure that continues the loop and a Groq failure that stops it. Ten decision points, zero tests. This is also the newest code in the repository and the error handling was rewritten most recently, which is exactly the combination that should worry someone.
Solution
Put a seam where the model choice happens: a one-method ChooseIcon trait with the Groq call behind it, and have the resolver take a notifier callback rather than an AppHandle. The pipeline stages, discovery, choice, persistence and notification, stay where they are; only the two that reach outside the process move behind adapters.
Benefits
The interface becomes the test surface. Each branch turns into a sentence a test can state: a repository with no artwork records its hash and emits nothing, a refusal keeps the fallback, a rejected key stops the pass instead of firing one doomed request per project. Locality improves too, because the retry policy stops being spread between the resolver and the shape of the Workspace store.
Worth being honest about the cost. One adapter is a hypothetical seam; two make it real. Here the second adapter is a test double, which is the weaker justification for a seam. Ten untested decision points in the newest code is what tips it.

C. The IPC seam has one interface spread across five files

Strong
Files
contract.rs, commands.rs, error.rs, shared/contract.ts, lib/ipc.ts
Problem
Both contract files open with a comment calling themselves the mirror of the other. Only half of that is true. The response types do mirror contract.rs, but the four request shapes on the TypeScript side, GetFileContentsRequest, GetHistoryRequest, StageFileRequest and IpcFailure, have no counterpart there at all. Their Rust definitions live in commands.rs and error.rs. Adding one command means editing five files, and nothing checks that any of them agree.
I compared the two files field by field while writing this. They are in sync today, so this is prevention rather than a live defect. The failure mode is quiet: a field added on one side and forgotten on the other typechecks on both sides and fails at runtime.
Solution
Derive the TypeScript from the Rust, with ts-rs or tauri-specta, so the interface has one definition and the second adapter is generated rather than maintained. If that is too much for now, the cheap version is a test that parses both files and asserts the field sets match, which is roughly twenty lines and catches the same class of drift.
Benefits
Locality for the whole seam: one place to change a payload instead of five to remember. Leverage for callers, since the command names and their argument shapes stop being three separate facts to keep in your head. The test story is the clearest part, because drift moves from something a reviewer has to notice to something CI fails on.

D. One invariant, two implementations: repository-relative path safety

Worth exploring
Files
services/diff.rs (is_safe_repo_path), services/project_icon.rs (is_safe_relative)
Problem
Both enforce the same rule, that a path must stay inside the repository, and they do it differently. is_safe_repo_path works on a string and rejects an empty value, a leading separator, a Windows drive letter, and any .. segment. is_safe_relative works on a Path and requires every component to be Normal. They disagree on real input: ./assets/icon.png passes the first and fails the second. Neither is wrong, but the rule now lives in two places, and tightening it later means finding both.
Solution
One path-safety module both call, with the two entry points kept because the callers genuinely differ: paths arrive from the renderer as strings and from git ls-files as paths.
Benefits
Locality for a security-relevant rule, which is the kind worth having in one place. The leverage is small, two callers, which is why this is worth exploring rather than urgent. Both call sites already have a test, so those tests move rather than multiply.

Top recommendation

Start with A. It is the smallest change, it sits in the most-edited file in the repository, and it is the only one of the four where three copies of the same operation are already behaving differently in shipped code. It also has the cleanest deletion test in both directions: removing OtherProjectsSection moves complexity rather than concentrating it, which marks it as shallow, while removing the proposed module would scatter the sequence back across three files, which marks that one as earning its keep.

Take B next, and take it seriously. A is about tidiness; B is about not knowing whether the newest code in the repository works. Ten decision points with no test, in error-handling logic that changed most recently, is the highest correctness risk here.

C is prevention and can wait for the next time someone adds a command, which is the moment its cost is felt. D is worth doing whenever project_icon.rs is next open.
